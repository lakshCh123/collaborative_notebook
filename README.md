# Offline Sync Conflict: When Devices Disagree

A backend that synchronizes edits to a notebook made from multiple devices. It detects conflicts instead of silently overwriting data, merges changes that can safely coexist, and reports exactly what happened to every change.

**Stack:** NestJS 12 (TypeScript, ESM) · Supabase (Postgres) · class-validator · Swagger/OpenAPI

## 1. Data model

A **document** (notebook) has a title and a set of **subtitles** (sections). Each subtitle has a `title` and `content`. Subtitles are stored as a JSON object keyed by subtitle ID inside the document row.

| Table | Purpose |
|---|---|
| `documents` | Current state: `id`, `title`, `subtitles` (JSONB), `version`, `device_id`, `created_at`, `updated_at` |
| `document_versions` | One immutable snapshot per accepted change, keyed by `document_id` + `version_number` |
| `sync_requests` | Idempotency log: `request_id`, `request_hash`, `status`, stored `response`, `device_id`, `document_id` |

Each subtitle stored on the server looks like:

```json
{
  "id": "bcae7d8e-38dd-4e17-89e7-8e08f4d69abc",
  "title": "Introduction",
  "content": "Hello",
  "version": 3,
  "created_at": "2026-10-03T10:00:00.000Z",
  "updated_at": "2026-10-03T11:00:00.000Z",
  "last_modified_device_id": "laptop-01"
}
```

The schema lives in `supabase/migrations/`.

## 2. How synchronization works

1. A device creates a document with `POST /documents`.
2. The device edits locally, possibly offline, and remembers the state each edit started from.
3. When it reconnects, it sends `PUT /documents` containing, for every subtitle it touched, its new values **and** the values it started from (`base_title`, `base_content`, `base_version`).
4. The server loads the current document and compares, subtitle by subtitle and field by field, the **incoming**, **base** and **current** values.
5. Non-conflicting changes are applied. Conflicting changes are left untouched and returned to the client with the values needed to resolve them.
6. If anything changed, the document is saved and a history snapshot is written in a single atomic database call.
7. The response lists what was `added`, `updated`, left `unchanged`, or put in `conflicts`.

Every write request carries two headers:

| Header | Purpose |
|---|---|
| `x-device-id` | Identifies the device. Stored as `last_modified_device_id` on each modified subtitle. |
| `idempotency-key` | A client-generated UUID that makes retries safe (see [section 7](#7-consistency-and-edge-cases)). |

## 3. How changes are tracked

- **Per-subtitle `version`.** Starts at 1 when a subtitle is created and increases by 1 each time its title or content actually changes.
- **Document `version`.** Increases by 1 once per accepted merge, regardless of how many subtitles changed in it.
- **Base values from the client.** Each edited subtitle is sent with `base_title`, `base_content` and `base_version`, which tell the server what state the edit was made from. This is what lets the server tell a *stale* edit from a *conflicting* one.
- **Device attribution.** `last_modified_device_id` records which device last changed each subtitle, and conflict reports include it.
- **Server-controlled timestamps and versions.** Merge-path versions and timestamps are generated by the server, so a device's clock cannot affect ordering.
- **History.** Every accepted change writes a full snapshot to `document_versions` in the same transaction as the update.

## 4. How conflicts are detected

Detection is a **three-way, field-level comparison** done per subtitle, separately for `title` and `content`:

```
clientChanged = incoming.field !== incoming.base_field   // did this device change it?
serverChanged = current.field  !== incoming.base_field   // did anyone else change it since?
```

| Client changed? | Server changed? | Result |
|---|---|---|
| No | any | Keep the server value. Nothing to apply for this field. |
| Yes | No | **Accept** the client value. |
| Yes | Yes, and the values are identical | **Accept.** Both devices made the same edit, so there is nothing to resolve. |
| Yes | Yes, and the values differ | **Conflict.** The server value is kept and the conflict is reported. |

Two consequences matter:

- **Staleness alone is not a conflict.** A device may be many versions behind. If the fields it edited were not touched by anyone else, its change is merged. `base_version` is not used as the conflict test; the field values are.
- **Order of arrival does not matter.** Because the decision depends on values rather than arrival time, changes that arrive out of order give the same result.

A single request can mix outcomes. Clean subtitles are saved and conflicting ones are reported in the same response.

A subtitle ID the server has not seen is treated as **new** and added with version 1.

---

## 5. Conflict-resolution strategy

**Field-level three-way merge. True conflicts are rejected and returned to the client for manual rebase.** The server never overwrites a newer accepted value.

Why this approach:

- **Predictable.** The same inputs always give the same result, whichever device syncs first.
- **No silent data loss.** A losing edit is returned to the client in full, never dropped.
- **Minimal conflicts.** Working per field avoids flagging edits that don't actually overlap.

**Resolving a conflict.** The conflict entry gives the client `baseValue`, `currentValue` and `incomingValue`. The client then:

1. Decides which value to keep, or combines them.
2. Re-sends the subtitle with `base_title` / `base_content` set to the `currentValue` it received, and `title` / `content` set to the chosen value.
3. Because the base now matches the server, the second request is accepted.

To simply accept the server's value, the client discards its local edit and does nothing further.

## 6. Conflicting and non-conflicting scenarios

Assume a subtitle currently has `title = "Intro"`, `content = "v1"`, `version = 1` and both devices start from that state.

| # | Scenario | Outcome |
|---|---|---|
| A | Device A changes the **title**, then Device B (still on the old state) changes the **content** | **Merged.** Both changes kept: title from A, content from B. Subtitle version 3. |
| B | Both devices change the **content** to different values | **Conflict** on `content`. The first accepted value stays. The second device gets the conflict details. |
| C | Both devices change the **content** to the **same** value | **No conflict.** Reported as unchanged for the second device. |
| D | A device sends a subtitle it did not edit, with old base values | **Unchanged.** The server's newer value is preserved. |
| E | A request has one clean subtitle and one conflicting subtitle | The clean one is **applied**, the conflicting one is **reported**. |
| F | A device sends a subtitle ID the server doesn't know | **Added** as version 1. |
| G | The same request is sent twice with the same `idempotency-key` | The stored result is replayed. Nothing is applied twice. |
| H | A subtitle has `base_version` greater than the server's current version | Rejected as an invalid future base version, reported in `conflicts`. |

## 7. Consistency and edge cases

| Situation | How it is handled |
|---|---|
| **Same request sent more than once** | The `idempotency-key` and a SHA-256 hash of the body are stored. Same key and same body replays the saved response with no second write. Same key with a different body returns **409**. |
| **Requests arriving close together** | The save uses an expected-version check (`p_expected_version`) in the database function. If another request changed the document first, the save is refused with SQLSTATE `40001` and the API returns **409** asking the client to fetch the latest state and retry. |
| **Duplicate in flight** | A unique constraint on `request_id` stops two copies of the same request from both running. The second gets **409**. |
| **Changes arriving out of order** | The merge compares values to the client's base, not arrival time, so order does not change the outcome. |
| **Device updating outdated data** | Safe fields merge. Overlapping fields are reported as conflicts. |
| **Two devices editing the same data** | Different fields merge. The same field with different values is a conflict. |
| **A newer change being overwritten** | Never done for subtitle title or content. A subtitle is only written when the incoming change is non-conflicting. |
| **Invalid input** | Rejected before any write. Unknown fields are stripped and rejected by validation, so nothing reaches the database. |
| **Atomicity** | Document update and history snapshot happen in one database call, so either both succeed or neither does. |

## 8. API reference

Interactive docs (Swagger UI): `http://localhost:3000/api`

| Method | Path | Required headers | Description |
|---|---|---|---|
| `POST` | `/documents` | `idempotency-key`, `x-device-id` | Create a document with its initial subtitles |
| `PUT` | `/documents` | `idempotency-key`, `x-device-id` | Sync a device's edits into an existing document |
| `GET` | `/documents/:documentId/versions` | `idempotency-key` | List all history snapshots, newest first |

`idempotency-key` must be a valid UUID.

**Status codes**

| Code | Meaning |
|---|---|
| `200` / `201` | Request processed. For `PUT`, inspect `conflicts` in the body. A `200` does not guarantee that every change was applied. |
| `400` | Invalid body, invalid UUID, or missing/invalid `idempotency-key` |
| `404` | Document not found |
| `409` | Idempotency key reused with a different body, request still in progress, document modified concurrently, or a duplicate document UUID on create |
| `500` | Database or unexpected error |

**`PUT /documents` body**

| Field | Type | Notes |
|---|---|---|
| `uuid` | UUID | Document being updated |
| `title` | string | New document title |
| `version` | integer ≥ 1 | Document version the client is updating from |
| `subtitles[]` | array | One entry per subtitle the device touched |
| `subtitles[].id` | UUID | Subtitle ID |
| `subtitles[].title`, `.content` | string | Values after the edit (`title` must be non-empty) |
| `subtitles[].base_version` | integer ≥ 1 | Subtitle version the edit started from |
| `subtitles[].base_title`, `.base_content` | string | Values the edit started from. **Required for any existing subtitle.** |

**`PUT /documents` response**

| Field | Meaning |
|---|---|
| `message` | Human-readable summary |
| `documentId`, `documentVersion`, `deviceId` | Identity and resulting document version |
| `added` | IDs of subtitles created by this request |
| `updated` | IDs of subtitles changed (fully or partly) |
| `unchanged` | IDs where there was nothing to apply |
| `conflicts` | Subtitles (or fields) that need resolution, with details |
| `data` | The stored document after the request |

## 9. Example requests and responses

Replace the UUIDs and `localhost:3000` as needed.

### 9.1 Create a document

```bash
curl -X POST http://localhost:3000/documents \
  -H "Content-Type: application/json" \
  -H "idempotency-key: 11111111-1111-4111-8111-111111111111" \
  -H "x-device-id: laptop-01" \
  -d '{
    "uuid": "7e1c8d65-0c51-4b3f-a7b8-123456789abc",
    "title": "Project Notes",
    "subtitles": [
      {
        "id": "bcae7d8e-38dd-4e17-89e7-8e08f4d69abc",
        "title": "Intro",
        "content": "v1",
        "base_title": "Intro",
        "base_content": "v1",
        "base_version": 1
      }
    ]
  }'
```

Response `201`:

```json
{
  "id": "7e1c8d65-0c51-4b3f-a7b8-123456789abc",
  "title": "Project Notes",
  "version": 1,
  "device_id": "laptop-01",
  "subtitles": {
    "5d0f3c0a-6b1e-4a52-9a43-0c6f5b7a1e21": {
      "id": "5d0f3c0a-6b1e-4a52-9a43-0c6f5b7a1e21",
      "title": "Intro",
      "content": "v1",
      "version": 1,
      "created_at": "2026-10-03T10:00:00.000Z",
      "updated_at": "2026-10-03T10:00:00.000Z",
      "last_modified_device_id": "laptop-01"
    }
  },
  "created_at": "2026-10-03T10:00:00.000Z",
  "updated_at": "2026-10-03T10:00:00.000Z"
}
```

> The server assigns its own IDs to subtitles created through `POST`. Use the IDs in the response in later `PUT` requests.

### 9.2 Non-conflicting merge (scenario A)

Device A renames the subtitle:

```bash
curl -X PUT http://localhost:3000/documents \
  -H "Content-Type: application/json" \
  -H "idempotency-key: 22222222-2222-4222-8222-222222222222" \
  -H "x-device-id: laptop-01" \
  -d '{
    "uuid": "7e1c8d65-0c51-4b3f-a7b8-123456789abc",
    "title": "Project Notes",
    "version": 1,
    "subtitles": [{
      "id": "5d0f3c0a-6b1e-4a52-9a43-0c6f5b7a1e21",
      "title": "Overview", "content": "v1",
      "base_title": "Intro", "base_content": "v1", "base_version": 1
    }]
  }'
```

Then Device B, still on the old state, edits only the content:

```bash
curl -X PUT http://localhost:3000/documents \
  -H "Content-Type: application/json" \
  -H "idempotency-key: 33333333-3333-4333-8333-333333333333" \
  -H "x-device-id: phone-01" \
  -d '{
    "uuid": "7e1c8d65-0c51-4b3f-a7b8-123456789abc",
    "title": "Project Notes",
    "version": 1,
    "subtitles": [{
      "id": "5d0f3c0a-6b1e-4a52-9a43-0c6f5b7a1e21",
      "title": "Intro", "content": "v2",
      "base_title": "Intro", "base_content": "v1", "base_version": 1
    }]
  }'
```

Response `200` for Device B (the title edit from Device A is preserved):

```json
{
  "message": "Merge completed successfully",
  "documentId": "7e1c8d65-0c51-4b3f-a7b8-123456789abc",
  "documentVersion": 3,
  "deviceId": "phone-01",
  "added": [],
  "updated": ["5d0f3c0a-6b1e-4a52-9a43-0c6f5b7a1e21"],
  "unchanged": [],
  "conflicts": [],
  "data": { "...": "document with title 'Overview' and content 'v2'" }
}
```

### 9.3 Conflict (scenario B)

Device B had edited content to `"v2"` and been accepted. Now Device A, still on the original state, edits the same field to a different value:

```bash
curl -X PUT http://localhost:3000/documents \
  -H "Content-Type: application/json" \
  -H "idempotency-key: 44444444-4444-4444-8444-444444444444" \
  -H "x-device-id: laptop-01" \
  -d '{
    "uuid": "7e1c8d65-0c51-4b3f-a7b8-123456789abc",
    "title": "Project Notes",
    "version": 1,
    "subtitles": [{
      "id": "5d0f3c0a-6b1e-4a52-9a43-0c6f5b7a1e21",
      "title": "Intro", "content": "my version",
      "base_title": "Intro", "base_content": "v1", "base_version": 1
    }]
  }'
```

Response `200`. Nothing is overwritten and the conflict is reported:

```json
{
  "message": "Merge completed with unresolved conflicts",
  "documentId": "7e1c8d65-0c51-4b3f-a7b8-123456789abc",
  "documentVersion": 2,
  "deviceId": "laptop-01",
  "added": [],
  "updated": [],
  "unchanged": [],
  "conflicts": [
    {
      "subtitleId": "5d0f3c0a-6b1e-4a52-9a43-0c6f5b7a1e21",
      "reason": "Concurrent edits to the same field",
      "currentVersion": 2,
      "baseVersion": 1,
      "fields": [
        {
          "field": "content",
          "baseValue": "v1",
          "currentValue": "v2",
          "incomingValue": "my version"
        }
      ],
      "existingDeviceId": "phone-01",
      "incomingDeviceId": "laptop-01"
    }
  ],
  "data": { "...": "unchanged document" }
}
```

**Resolving it:** Device A chooses a value and re-sends with the base set to the server's `currentValue`:

```json
{
  "id": "5d0f3c0a-6b1e-4a52-9a43-0c6f5b7a1e21",
  "title": "Intro",
  "content": "v2 plus my notes",
  "base_title": "Intro",
  "base_content": "v2",
  "base_version": 2
}
```

This is accepted, because the base now matches the server.

### 9.4 Duplicate request

Re-sending any request with the same `idempotency-key` and the same body returns the stored result without applying it again:

```json
{
  "message": "Same request already processed",
  "data": { "...": "the original response" }
}
```

The same key with a **different** body returns `409`:

```json
{ "statusCode": 409, "message": "Idempotency key reused with a different request body", "error": "Conflict" }
```

### 9.5 Concurrent modification

```json
{
  "statusCode": 409,
  "message": "Document was modified by another request. Fetch the latest version and retry.",
  "error": "Conflict"
}
```

### 9.6 Version history

```bash
curl http://localhost:3000/documents/7e1c8d65-0c51-4b3f-a7b8-123456789abc/versions \
  -H "idempotency-key: 55555555-5555-4555-8555-555555555555"
```

```json
{
  "message": "Document versions retrieved successfully",
  "documentId": "7e1c8d65-0c51-4b3f-a7b8-123456789abc",
  "totalVersions": 3,
  "versions": [ { "version_number": 3, "...": "..." } ]
}
```

### 9.7 Validation and not-found errors

| Request | Response |
|---|---|
| Missing or non-UUID `idempotency-key` | `400` "A valid UUID is required in the idempotency-key header" |
| Unknown field in body | `400` from the validation pipe |
| `PUT` for a document that doesn't exist | `404` "Notebook ... was not found" |

## 10. Setup and running

**Prerequisites:** Node.js 20+, a Supabase project (or local Supabase via the CLI).

```bash
# 1. Install dependencies
npm install

# 2. Configure environment
cp ".env example" .env
#    then edit .env:
#      SUPABASE_URL=https://<your-project>.supabase.co
#      SUPABASE_SECRET_KEY=<service role / secret key>
#      PORT=3000

# 3. Create the database objects (tables and the update_document_with_history function)
npx supabase db push        # or run supabase/migrations/*.sql in the Supabase SQL editor

# 4. Start the server
npm run start:dev

# Swagger UI
open http://localhost:3000/api
```

Other scripts: `npm run build`, `npm run start:prod`, `npm run lint`, `npm run format`, `npm test`.
